## 一、项目背景

### 1.1 业务背景

传统文旅行业的行程规划，靠**人工查资料 + Excel 排行程**。旅行顾问接到一个需求（比如"7天云南家庭游"），要手动：

1. 上网搜景点、酒店、交通、天气
2. 看景点口碑、避开差评和消费陷阱
3. 逐天排行程、算预算
4. 检查有没有风险（夜行、超预算）

一个行程从需求到方案，往往要**几小时到一整天**，而且：

- **数据是静态的**——查到的信息可能已经过时
- **没有风险拦截**——可能推荐了有严重差评的景点、超预算的行程
- **没有容灾**——查到一半电脑崩了，前面的工作全丢

### 1.2 技术背景

这是一个人工智能课程/实训项目的**工单任务**，属于「多 Agent 协同」系列。项目分两期：

- **多 Agent-2（本文主体）**：文旅资源调研与个性化行程规划系统
- **工单 7（叠加）**：跨系统协同共享图记忆与运行态强干预系统

要求用 **LangGraph + 多 Agent** 技术栈，把一个"人工排行程"的场景，改造成"AI 自动调研 + 编排 + 生成"的异步任务系统。

### 1.3 工期约束

- **1 个人**，独立完成
- v1.0 工期 **7 人日**（周一~周五，每天约 1.4 人日折算）
- 工单 7 增量工期 **3 人日**

在这个极紧的工期下，必须做大量**「最小增量、最大复用」**的取舍决策。

## 二、项目痛点

### 痛点 1：语义遗忘（工单 7 点名的核心痛点）

> 用户第 1 次说"我母亲海鲜严重过敏"，系统记住了；两周后用户再来做"青岛游"，系统**忘了**过敏这件事，推荐了一堆海鲜餐厅。

**本质**：传统 Agent 系统**没有长期记忆**，每次对话都是"失忆"状态。用户必须反复重复自己的偏好、约束、过敏史。

### 痛点 2：检查点状态不刷新

> 系统正在跑一个行程，某景点突然"台风停运"（或某货车故障停运——工单7原文映射到文旅就是"景点封闭"），但系统**不知道**，还在按旧信息继续编排，把已停运的景点排进行程。

**本质**：运行中的 Agent 状态是"冻结"的，没有**运行态纠偏**能力。

### 痛点 3：长任务无容灾

> 行程规划要跑几分钟（8 个 Agent 依次执行），跑到一半进程崩了，**前面所有工作全丢**，得从头再来。

**本质**：缺少**断点续传**机制。

### 痛点 4：纯人工，无风险拦截

> 人工排行程时，可能无意中推荐了**有严重差评的景点**、**超预算 20% 的行程**、**夜间高危路段**，没有系统化拦截。

**本质**：缺少**人机协作门控（HITL）**。

### 痛点 5：假数据、假智能

> 早期版本的 Agent 用"写死的种子数据"和"Mock LLM"，看起来能跑，但**景点是假的、路线是假的、推理是假的**，没有真实价值。

**本质**：缺少**真实数据源接入**。

## 三、项目目标与需求

### 3.1 一句话目标

**把一个"人工排行程"的活，改造成"AI 自动调研工厂"**：输入一句自然语言需求，8 个 AI Agent 自动完成调研、编排、预算、报告，全程真实数据、可断点续传、可人工审核、可长期记忆。

### 3.2 核心功能需求

| # | 需求 | 说明 |
|---|---|---|
| 1 | 8 个 Agent 协同编排 | 偏好解析→任务拆解→网页调研→舆情评估→日程编排→预算计算→人工审核→报告生成 |
| 2 | planning-with-files 断点续传 | 全程持久化到 `travel_plan.md`，崩溃 5 秒内恢复 |
| 3 | 五状态机 + 原子写入 | planning/running/suspended/recovering/completed + failed/cancelled |
| 4 | HITL 人机协作 | 超预算20%/高危夜行/严重舆情 → 挂起人工审核 |
| 5 | 安全 | 内容过滤 + 防 Prompt 注入 |
| 6 | 压测达标 | QPS≥200 / P95<300ms / 错误率<0.1% |
| 7 | 图记忆（工单7） | 跨行程沉淀知识图谱，修复语义遗忘 |
| 8 | 运行态强干预（工单7） | 主管带验签地修改运行中状态，修复状态不刷新 |
| 9 | 真实高德数据 | 景点/路线/天气/营业时间/图片全真实（高德 API） |
| 10 | 完整行程规划 | 每日三餐餐饮推荐 + 景点图片 + 营业时间 + 出发/返程日期自动算天数 |

- 检索 P95 < 150ms、干预成功率 100%（工单 7 红线）
- Docker 一键启动
- JWT 鉴权 + RBAC 权限分离

## 四、技术难点

### 难点 1：断点续传的正确性

**难点**：进程随时可能崩溃（kill -9），怎么保证"不丢进度、不重复执行"？

**解法**：
- 原子写入：临时文件 → `fsync` → `os.replace` → 目录 fsync，任何时刻崩溃文件要么旧版要么新版，绝不"半份"
- checksum 校验 + 快照回退（保留最近 5 版）
- 幂等恢复：已 `completed` 且已落库的任务不重跑，只重跑无持久化结果的当前任务

### 难点 2：异步队列的崩溃接管

**难点**：Worker 崩了，它正在处理的消息怎么办？

**解法**：Redis Streams 的 consumer group + **PEL（pending entries list）+ XAUTOCLAIM**，崩溃 worker 的未确认消息会被自动认领转给存活 worker。

### 难点 3：审核并发（防重复审批）

**难点**：两个主管同时点"审批通过"同一个行程，怎么防止重复审批、状态错乱？

**解法**：**锁降冲突、DB 条件更新保正确**——
- Lua CAS 抢占（Suspended→Reviewing 原子转换）
- DB 条件更新 `WHERE decision='pending'` 才是正确性保证
- 会话租约锁（5分钟可续期）+ token 校验防误删

### 难点 4：写入-入队竞态（容器化才暴露）

**难点**：API 写入行程后立即入队，Worker 抢在 DB commit 前消费，报"行程不存在"。

**解法**：入队前显式 `await db.commit()`。这个 bug 本地单进程测试**永远发现不了**，只有容器化多进程才暴露。

### 难点 5：图记忆的抽取与检索

**难点**：怎么把自然语言"我香菜过敏"抽成结构化三元组？怎么跨行程召回？

**解法**：
- **真实 LLM 抽取**（不限过敏原白名单，香菜/花粉/青霉素都能识别）
- 三元组 upsert 沉淀（`(src_key,dst_key,relation)` 命中即合并）
- 向量 + 图拓扑双路检索 + Redis 缓存（P95 0.3ms）

### 难点 6：运行态强干预的安全与原子性

**难点**：怎么让主管"改运行中的状态"，既不越权、又不产生并发错乱？

**解法**：HMAC 验签 + nonce 防重放 + SETNX 排他锁 + 三写一事务 + 节点入口应用补丁。

### 难点 7：真实数据接入的坑

**难点**：第三方 API 有各种坑（key 类型、参数格式、限流、编码）。

**解法**（实践中踩过的坑）：
- 高德 `_url` 函数最初忘了拼 params，key 根本没发出去
- 高德偶发 `INVALID_USER_KEY`，需要重试机制
- 百炼 `json_object` 模式要求 messages 里含 "json" 字样，否则 400
- nginx 缓存容器旧 IP 导致 502，需 Docker DNS 动态解析

## 八、核心技术实现

### 8.1 断点续传

- 全程持久化到 `workspace/{plan_id}/travel_plan.md`
- YAML 头含 `version`、`checksum`、`status`、`resume_from`
- 原子写入：临时文件 → fsync → `os.replace` → 目录 fsync
- 快照回退：保留最近 5 版，checksum 失败自动回退
- 崩溃恢复：Worker 启动扫描 running/recovering → 读 resume_from → 跳过已完成任务续跑

### 8.2 状态机

```
planning → running → suspended → completed
              ↓          ↓
         recovering   rejected(驳回)
              ↓
            failed / cancelled
```

### 8.3 HITL 人机协作

三个触发条件（超预算20% / 高危夜行 / 严重舆情）→ 挂起，主管在审核台抢占/通过/驳回。

- 抢占用 Lua CAS（Suspended→Reviewing 原子转换）
- 挂起后 Worker 释放（不阻塞），审批通过重新入队续跑
- 审批超时（24h）自动驳回

### 8.4 图记忆（工单 7）

```
实体抽取 → 三元组 upsert → 向量+图双路检索
```

- 实体抽取：真实 LLM 抽取（支持任意过敏原）
- 三元组：`(User:用户)-[HAS_ALLERGY]->(Food:香菜)`
- 双路检索：向量相似 + 图拓扑 1 跳邻域，Redis 缓存 60s
- 检索耗时：P95 = 0.3ms

### 8.5 运行态强干预（工单 7）

```
HMAC 验签 → nonce 防重放 → SETNX 排他锁 → 三写一事务 → 节点入口应用补丁
```

### 8.6 安全

- JWT + RBAC（advisor 创建/查询，supervisor 审核/干预）
- Prompt 注入检测（规则引擎 + 结构隔离 + 工具白名单）
- 网页内容安全过滤（独立模块）
- HMAC 验签 + nonce 防重放（干预接口）

顾问提交"3天杭州游"→ 8 Agent 执行 → 报告含天气+路线+每日行程+酒店+预算

### 场景 B：崩溃恢复

Web Research 跑到第 6 页 kill -9 → 重启 → 从第 7 页续跑，前 6 页不重复

### 场景 C：注入拦截

第 7 页含"忽略之前指令"对抗样本 → 拦截 → 标记 blocked → 写审计日志

### 场景 D：HITL 人工审核

超预算/夜行/舆情 → 挂起 → 主管抢占 → 通过 → 续跑出报告

### 场景 E：图记忆 + 强干预

1. 行程 1 说"我母亲海鲜严重过敏"→ 抽成三元组入图
2. 行程 2（未再提）→ 检索召回过敏约束 → 避开海鲜
3. 主管干预"栈桥台风停运"→ 运行中行程自动剔除该景点

## 十四、设计决策记录

项目在 7 人日 + 3 人日的极紧工期下，做了大量「最小增量、最大复用」的取舍（完整 31 条 S 决策 + 16 条 D 决策见需求文档，此处摘录关键）：

| 决策 | 内容 | 理由 |
|---|---|---|
| 编排框架 | LangGraph | 工单首选，7人日不允许自研图引擎 |
| 队列 | Redis Streams | 工单指定，PEL 原生支持断点 |
| LLM | 抽象 Provider，Mock→真实切换 | 压测不烧钱，演示切真模型 |
| 文件布局 | 每行程一目录 | 避免并发写冲突 |
| 恢复粒度 | task/网页级 | 满足验收，ReAct step 级是加分 |
| 图存储 | PostgreSQL（应用层向量） | 延续单机原则，不引 Neo4j/pgvector |
| 记忆引擎 | 自研轻量 Mem0 风格 | 3人日不允许消化外部框架黑盒 |
| 干预 | HMAC + nonce + 三写事务 | 工单验收红线：安全验签 |
